# TO-BE Analysis

## 1. Описание целевого процесса

Целевой процесс автоматизирует обработку закупочных заявок и устраняет проблемы, выявленные при анализе текущего процесса (AS-IS).

Внедрение системы управления закупочными заявками позволяет:

- **централизовать** создание, хранение и обработку заявок;
- **автоматизировать** проверку заполнения обязательных полей;
- **автоматически определять** маршрут согласования на основе типа закупки;
- **отслеживать статус** заявки в режиме реального времени;
- **сохранять полную историю** всех действий с заявкой;
- **уведомлять** участников о необходимости выполнения действий.

Целевой процесс включает следующие этапы:

1. Сотрудник создаёт заявку в системе.
2. Система проверяет заполнение обязательных полей.
3. Сотрудник отправляет заявку на согласование.
4. Система автоматически определяет маршрут согласования.
5. Система направляет заявку первому согласующему.
6. Согласующий принимает решение (согласовать, отклонить, вернуть на доработку).
7. Система автоматически направляет заявку на следующий этап.
8. После завершения всех этапов заявка передаётся в отдел закупок.
9. На каждом этапе система фиксирует действия в истории и отправляет уведомления.

---

## 2. Сравнение AS-IS и TO-BE

| Аспект | AS-IS (текущий процесс) | TO-BE (целевой процесс) |
| :--- | :--- | :--- |
| **Создание заявки** | Вручную, в произвольном формате (Word, Excel, email) | Через стандартизированную форму в системе |
| **Передача заявки** | По электронной почте, вручную | Автоматически, через систему |
| **Проверка заявки** | Ручная проверка руководителем | Автоматическая проверка обязательных полей + ручная проверка руководителем |
| **Определение маршрута** | Ручное, руководителем | Автоматическое, на основе типа закупки |
| **Статус заявки** | Отсутствует (нужно спрашивать у участников) | Отображается в системе в реальном времени |
| **История заявки** | Разрознена по email-переписке | Централизованно хранится в системе |
| **Уведомления** | Отсутствуют (участники узнают о заявке по email) | Автоматические уведомления внутри системы и по email |
| **Контроль сроков** | Отсутствует | Фиксация времени на каждом этапе, уведомления о просрочках |

## 3. Основные этапы TO-BE процесса

### 3.1. Создание и отправка заявки

| Шаг | Действие | Ответственный | Как в системе |
| :--- | :--- | :--- | :--- |
| 1 | Создание заявки | Сотрудник | Заполнение формы в системе |
| 2 | Проверка обязательных полей | Система | Автоматическая валидация |
| 3 | Сохранение черновика (опционально) | Сотрудник | Сохранение без отправки |
| 4 | Отправка на согласование | Сотрудник | Нажатие кнопки "Отправить" |
| 5 | Определение маршрута | Система | Автоматически по типу закупки |
| 6 | Создание первого этапа | Система | Назначение ответственному согласующему |
| 7 | Уведомление согласующего | Система | Внутреннее уведомление + email |

**Отличие от AS-IS:**
- Вместо отправки по email — отправка через систему.
- Вместо ручной проверки руководителем — автоматическая проверка системой.
- Вместо ручного определения маршрута — автоматическое определение.

---

### 3.2. Согласование заявки

| Шаг | Действие | Ответственный | Как в системе |
| :--- | :--- | :--- | :--- |
| 1 | Получение уведомления | Согласующий | Внутреннее уведомление + email |
| 2 | Просмотр заявки | Согласующий | Открытие заявки в системе |
| 3 | Изучение документов | Согласующий | Просмотр и скачивание файлов |
| 4 | Принятие решения | Согласующий | Выбор: Согласовать / Вернуть / Отклонить |
| 5 | Указание причины (при возврате/отклонении) | Согласующий | Заполнение обязательного поля |
| 6 | Оставление комментария (опционально) | Согласующий | Текстовое поле |
| 7 | Сохранение решения | Система | Запись в историю |
| 8 | Изменение статуса заявки | Система | Автоматически |
| 9 | Определение следующего этапа | Система | Автоматически по маршруту |
| 10 | Уведомление участников | Система | Автору + следующему согласующему |

**Отличие от AS-IS:**
- Вместо ручной передачи по email — автоматическое направление на следующий этап.
- Вместо отсутствия комментариев — обязательная причина при возврате/отклонении.
- Вместо разрозненной информации — централизованная история всех решений.

---

### 3.3. Завершение заявки

| Шаг | Действие | Ответственный | Как в системе |
| :--- | :--- | :--- | :--- |
| 1 | Получение уведомления о согласовании | Отдел закупок | Внутреннее уведомление + email |
| 2 | Просмотр заявки | Отдел закупок | Открытие заявки в системе |
| 3 | Проверка документов | Отдел закупок | Просмотр и скачивание файлов |
| 4 | Принятие заявки | Отдел закупок | Нажатие кнопки "Принять заявку" |
| 5 | Изменение статуса | Система | Статус "Передана в отдел закупок" |
| 6 | Фиксация завершения | Система | Запись в истории |
| 7 | Уведомление автора и руководителя | Система | Уведомление о передаче в ОЗ |

**Отличие от AS-IS:**
- Вместо ручной передачи — автоматическое уведомление отдела закупок.
- Вместо отсутствия подтверждения — фиксация завершения в системе.
- Вместо неизвестности статуса — чёткое отображение "Передана в отдел закупок".

## 4. Устранение проблем AS-IS в TO-BE

| Проблема AS-IS | Решение в TO-BE | Как реализовано |
| :--- | :--- | :--- |
| **Передача по email** | Централизованная работа с заявками | Все заявки создаются, хранятся и обрабатываются в системе. Передача между этапами автоматическая. |
| **Ручная проверка** | Автоматическая валидация | Система проверяет обязательные поля перед отправкой и блокирует отправку, если поля не заполнены. |
| **Ручная маршрутизация** | Автоматическое определение маршрута | Система определяет маршрут по типу закупки. При отсутствии маршрута — уведомляет администратора. |
| **Отсутствие единого статуса** | Отображение статуса в реальном времени | Статус заявки виден всем участникам в системе. Изменяется автоматически при переходе между этапами. |
| **Отсутствие истории** | Централизованное хранение истории | Все действия фиксируются в `RequestHistory` и доступны для просмотра. |

## 5. Ключевые улучшения TO-BE

### 5.1. Автоматизация проверки

**AS-IS:** Руководитель вручную проверяет каждую заявку, тратит время на возврат и повторную проверку.

**TO-BE:** Система автоматически проверяет заполнение обязательных полей при сохранении и отправке. Если поля пустые — система показывает ошибку и блокирует отправку.

**Выгода:** Снижение количества циклов доработки, экономия времени руководителя.

---

### 5.2. Автоматическая маршрутизация

**AS-IS:** Руководитель вручную определяет, кому отправить заявку, и отправляет её по email.

**TO-BE:** Система автоматически определяет маршрут по типу закупки и направляет заявку на первый этап. При отсутствии маршрута — уведомляет администратора.

**Выгода:** Исключение ошибок маршрутизации, ускорение процесса.

---

### 5.3. Прозрачность статуса

**AS-IS:** Участники не знают статус заявки и вынуждены спрашивать друг у друга.

**TO-BE:** Статус заявки отображается в системе в реальном времени и обновляется автоматически.

**Выгода:** Снижение количества коммуникаций, повышение прозрачности.

---

### 5.4. Централизованная история

**AS-IS:** Информация о действиях разрознена по email-переписке.

**TO-BE:** Все действия фиксируются в `RequestHistory` и доступны для просмотра.

**Выгода:** Возможность восстановить полную картину процесса, анализ задержек.

---

### 5.5. Автоматические уведомления

**AS-IS:** Участники узнают о заявках по email в ручном режиме.

**TO-BE:** Система автоматически отправляет уведомления о новых задачах, изменениях статуса, приближении сроков.

**Выгода:** Своевременное реагирование, снижение риска просрочек.

## 8. Вывод

Внедрение системы управления закупочными заявками позволяет:

1. **Централизовать** процесс обработки заявок — все заявки создаются, хранятся и обрабатываются в единой системе.
2. **Автоматизировать** проверку заполнения обязательных полей — снижение количества ошибок и циклов доработки.
3. **Автоматически определять** маршрут согласования на основе типа закупки — исключение ошибок ручной маршрутизации.
4. **Обеспечить прозрачность** статуса заявки для всех участников — снижение количества коммуникаций.
5. **Сохранять полную историю** всех действий — возможность анализа процесса и восстановления картины.
6. **Автоматически уведомлять** участников о необходимости выполнения действий — своевременное реагирование.

Целевой процесс устраняет ключевые проблемы текущего процесса и создаёт основу для дальнейшего анализа эффективности закупочной деятельности.
