# Stakeholder Analysis

## 1. Заинтересованные стороны

В процессе обработки закупочных заявок участвуют несколько подразделений компании. Их задачи и потребности различаются в зависимости от этапа процесса.

| Stakeholder | Роль в процессе | Основная потребность |
|---|---|---|
| Сотрудник | Инициирует закупку и формирует заявку | Быстро создать заявку и отслеживать её статус |
| Руководитель | Проверяет заявку и принимает решение о дальнейшем согласовании | Получать корректные заявки и быстро принимать решения |
| Отдел закупок | Обрабатывает согласованные заявки | Получать полную и корректно оформленную информацию |
| IT | Проверяет IT-закупки | Получать необходимые технические данные для оценки |
| Финансовый департамент | Участвует в финансовом согласовании | Получать информацию, необходимую для оценки расходов |
| Юридический отдел | Проводит юридическую проверку | Получать необходимые данные и документы для проверки |
| Руководство компании | Заинтересовано в эффективности закупочного процесса | Контролировать расходы и эффективность процесса |
| IT-отдел компании | Обеспечивает работу информационных систем | Стабильная работа системы и корректное хранение данных |

## 2. Интересы и проблемы участников

### Сотрудник

**Интересы:**
- быстро оформить заявку;
- понимать, на каком этапе находится заявка;
- получать информацию о необходимости дополнительных действий.

**Проблемы:**
- заявка передаётся по электронной почте;
- нет единого места для отслеживания статуса;
- при возврате заявки необходимо повторно взаимодействовать с руководителем.

### Руководитель

**Интересы:**
- быстро проверять заявки;
- получать всю необходимую информацию для принятия решения;
- контролировать заявки, находящиеся на согласовании.

**Проблемы:**
- проверка выполняется вручную;
- заявки поступают по электронной почте;
- дальнейший маршрут необходимо определять вручную.

### Отдел закупок

**Интересы:**
- получать полностью согласованные заявки;
- иметь всю необходимую информацию для дальнейшей обработки;
- контролировать поступающие заявки.

**Проблемы:**
- информация может быть распределена между несколькими письмами;
- при отсутствии данных требуется дополнительное уточнение;
- отсутствует единое представление о статусе заявки.

### IT

**Интересы:**
- получать заявки с необходимой технической информацией;
- своевременно проводить техническую проверку.

**Проблемы:**
- необходимость дополнительно запрашивать недостающую информацию;
- участие в процессе зависит от корректной маршрутизации заявки.

### Финансовый департамент

**Интересы:**
- получать информацию о закупке для согласования;
- контролировать финансовую составляющую заявки.

**Проблемы:**
- информация может поступать через разные каналы;
- отсутствие единого рабочего пространства усложняет контроль заявок.

### Юридический отдел

**Интересы:**
- своевременно получать заявки, требующие юридической проверки;
- иметь полный комплект информации для принятия решения.

**Проблемы:**
- необходимость получать дополнительные данные при неполной заявке;
- отсутствие единого места для работы с заявками.

### Руководство компании

**Интересы:**
- прозрачность закупочных расходов;
- контроль эффективности процесса;
- возможность анализировать показатели закупок.

**Проблемы:**
- отсутствие централизованной информации;
- сложность получения общей картины по процессу;
- ограниченные возможности оперативного анализа.

### IT-отдел компании

**Интересы:**
- стабильная работа системы;
- сохранность и доступность данных;
- корректное разграничение доступа пользователей.

**Проблемы:**
- необходимость поддерживать систему и обеспечивать её доступность;
- необходимость учитывать различные роли пользователей.

## 3. Ключевые потребности

На основании рассмотрения ролей участников можно выделить несколько общих потребностей:

1. **Централизованная работа с заявками** — информация о заявке должна храниться в одном месте.
2. **Прозрачность статуса** — участники должны понимать текущее состояние заявки.
3. **Корректная маршрутизация** — заявка должна попадать к необходимым участникам процесса.
4. **Доступ к полной информации** — участники должны получать данные, необходимые для выполнения своей роли.
5. **История обработки** — должна сохраняться информация об основных действиях и изменениях заявки.

Эти потребности будут использоваться на следующих этапах проекта при формировании требований к целевой системе.
