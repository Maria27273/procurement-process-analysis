# Functional Requirements

## 1. Управление заявками

### FR-01. Система должна позволять сотруднику создавать закупочную заявку.

**Acceptance Criteria:**
- пользователь может создать новую заявку;
- заявке автоматически присваивается уникальный идентификатор;
- система не позволяет отправить заявку при отсутствии обязательных данных.

### FR-02. Система должна позволять сотруднику редактировать заявку до момента её отправки на согласование.

**Acceptance Criteria:**
- пользователь может изменять данные заявки в статусе «Черновик»;
- после отправки заявки на согласование редактирование недоступно инициатору;
- изменения сохраняются в заявке.

### FR-03. Система должна отображать пользователю информацию о заявках, доступных ему в соответствии с его ролью.

**Acceptance Criteria:**
- пользователь может открыть доступную ему заявку;
- система отображает основные данные заявки;
- пользователь не может просматривать заявки, к которым у него нет доступа.

## 2. Проверка и согласование

### FR-04. Система должна проверять заполнение обязательных полей перед отправкой заявки на согласование.

**Acceptance Criteria:**
- система определяет незаполненные обязательные поля;
- система не позволяет отправить заявку при наличии незаполненных обязательных полей;
- система отображает пользователю информацию об ошибках.

### FR-05. Система должна позволять руководителю принять решение по заявке.

Руководитель должен иметь возможность:
- согласовать заявку;
- вернуть заявку на доработку;
- отклонить заявку.

**Acceptance Criteria:**
- выбранное решение сохраняется в системе;
- при возврате заявки на доработку система изменяет её статус;
- при отклонении заявки система изменяет её статус;
- действие руководителя сохраняется в истории заявки.

## 3. Маршрутизация

### FR-06. Система должна определять маршрут обработки заявки в зависимости от выбранного типа закупки.

**Acceptance Criteria:**
- система определяет маршрут для каждого типа закупки;
- система направляет заявку следующему участнику в соответствии с определённым маршрутом;
- пользователь не должен вручную выбирать следующего участника стандартного маршрута.

### FR-07. Система должна направлять заявку на дополнительные этапы согласования в соответствии с установленным маршрутом.

**Acceptance Criteria:**
- IT-заявка направляется на техническое согласование;
- юридическая заявка направляется на юридическую проверку;
- после завершения дополнительного согласования система переводит заявку на следующий этап маршрута.

## 4. Статусы и уведомления

### FR-08. Система должна изменять статус заявки в соответствии с текущим этапом её обработки.

Основные статусы:

- Черновик
- На проверке
- На согласовании
- На доработке
- Согласована
- Отклонена
- Передана в отдел закупок

**Acceptance Criteria:**
- выполнение предусмотренного действия изменяет статус заявки;
- текущий статус отображается пользователю;
- каждое изменение статуса фиксируется в истории.

### FR-09. Система должна уведомлять участников процесса о необходимости выполнить действие с заявкой.

**Acceptance Criteria:**
- система уведомляет следующего участника после передачи заявки;
- система уведомляет инициатора при возврате заявки на доработку;
- уведомление содержит информацию о заявке и требуемом действии.

## 5. История обработки

### FR-10. Система должна сохранять историю обработки каждой заявки.

История должна содержать:
- дату и время действия;
- пользователя;
- выполненное действие;
- предыдущий и новый статус.

**Acceptance Criteria:**
- изменение статуса сохраняется в истории;
- для каждого действия фиксируются дата, время и пользователь;
- пользователь с соответствующими правами может просмотреть историю заявки.

## 6. Нестандартные маршруты

### FR-11. Система должна позволять ответственному пользователю добавлять дополнительные этапы согласования для нестандартных заявок.

**Acceptance Criteria:**
- пользователь с соответствующими правами может добавить дополнительный этап;
- добавленный этап отображается в маршруте заявки;
- добавленный этап фиксируется в истории;
- после завершения дополнительного этапа заявка продолжает обработку.

## 7. Поиск и просмотр заявок

### FR-12. Система должна позволять пользователю искать заявки по заданным параметрам.

Параметры поиска:

- идентификатор заявки;
- тип закупки;
- подразделение;
- статус;
- дата создания.

**Acceptance Criteria:**
- пользователь может выполнить поиск по одному параметру;
- пользователь может использовать несколько параметров одновременно;
- система отображает только заявки, соответствующие условиям поиска.

### FR-13. Система должна отображать пользователю список доступных ему заявок.

**Acceptance Criteria:**
- в списке отображаются идентификатор, тип закупки, дата создания и статус;
- список содержит только доступные пользователю заявки;
- пользователь может открыть заявку из списка.

## 8. Работа с документами

### FR-14. Система должна позволять пользователю прикреплять документы к закупочной заявке.

**Acceptance Criteria:**
- пользователь может добавить один или несколько файлов к заявке;
- прикреплённые файлы отображаются в карточке заявки;
- система сохраняет информацию о прикреплённых файлах.

### FR-15. Система должна позволять пользователю просматривать и скачивать документы, прикреплённые к заявке.

**Acceptance Criteria:**
- пользователь с соответствующими правами может открыть список документов;
- пользователь может скачать доступный ему документ;
- пользователь не может получить доступ к документам заявки, к которой у него нет доступа.

## 9. Комментарии и доработка

### FR-16. Система должна позволять участникам процесса оставлять комментарии к заявке.

**Acceptance Criteria:**
- пользователь может добавить комментарий к доступной ему заявке;
- комментарий сохраняется с указанием автора и даты;
- комментарий отображается в истории заявки.

### FR-17. Система должна позволять руководителю возвращать заявку на доработку с указанием причины возврата.

**Acceptance Criteria:**
- при возврате заявки руководитель указывает причину;
- причина сохраняется в системе;
- инициатор получает уведомление о возврате;
- заявка получает статус «На доработке».

## 10. Роли и права доступа

### FR-18. Система должна предоставлять пользователям доступ к функциям и данным в соответствии с их ролью.

**Acceptance Criteria:**
- пользователь может выполнять только предусмотренные его ролью действия;
- доступ к заявкам ограничивается установленными правилами;
- пользователь не может выполнять действия, недоступные его роли.

## 11. Контроль сроков

### FR-19. Система должна фиксировать время нахождения заявки на каждом этапе обработки.

**Acceptance Criteria:**
- для каждого этапа сохраняются время начала и завершения;
- система позволяет определить продолжительность каждого этапа;
- данные о времени обработки сохраняются вместе с историей заявки.

### FR-20. Система должна уведомлять ответственного пользователя о приближении установленного срока обработки заявки.

**Acceptance Criteria:**
- для этапа может быть установлен срок выполнения;
- система определяет приближение установленного срока;
- ответственный пользователь получает уведомление.

## 12. Завершение обработки

### FR-21. Система должна передавать согласованную заявку в отдел закупок после завершения всех обязательных этапов согласования.

**Acceptance Criteria:**
- система проверяет завершение обязательных этапов;
- после завершения всех этапов заявка получает статус «Передана в отдел закупок»;
- отдел закупок получает уведомление о поступлении заявки.

### FR-22. Система должна фиксировать результат обработки закупочной заявки.

**Acceptance Criteria:**
- для завершённой заявки фиксируется итоговый статус;
- дата завершения сохраняется в системе;
- информация о завершённой заявке доступна для последующего анализа.
