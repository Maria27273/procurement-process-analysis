# Use Cases

## UC-01. Создание закупочной заявки

**Область действия:** Система управления закупочными заявками

**Уровень:** Цели пользователя

**Основное действующее лицо:** Сотрудник

**Участники:** Отсутствуют

**Предусловие:** 
- Пользователь авторизован в системе.
- Пользователь имеет роль "Сотрудник".

**Гарантии успеха:** 
- Заявка создана и сохранена в системе.
- Заявке присвоен уникальный идентификатор.
- Заявка находится в статусе "Черновик".

**Триггер:** Сотрудник инициирует создание новой закупочной заявки.

**Описание:**
1. Сотрудник открывает раздел "Создание заявки".
2. Система отображает пустую форму заявки.
3. Сотрудник заполняет поля формы (тип закупки, описание, сумма, подразделение, обоснование).
4. Сотрудник прикрепляет необходимые документы (до 10 файлов).
5. Сотрудник нажимает кнопку "Сохранить как черновик".
6. Система проверяет заполнение обязательных полей.
7. Система сохраняет заявку со статусом "Черновик".
8. Система отображает сообщение об успешном сохранении и присваивает заявке уникальный идентификатор.

**Расширения:**
- *3a. Сотрудник не заполнил обязательные поля:*
  1. Система подсвечивает незаполненные поля.
  2. Система отображает сообщение: "Заполните все обязательные поля, отмеченные звёздочкой".
  3. Возврат к шагу 3.
- *4a. Сотрудник прикрепил файл недопустимого формата:*
  1. Система отображает сообщение: "Недопустимый формат файла. Поддерживаются: PDF, DOC, DOCX, XLS, XLSX, JPG, PNG".
  2. Возврат к шагу 4.
- *4b. Сотрудник прикрепил файл размером более 10 МБ:*
  1. Система отображает сообщение: "Размер файла превышает 10 МБ".
  2. Возврат к шагу 4.
- *4c. Сотрудник прикрепил более 10 файлов:*
  1. Система отображает сообщение: "Максимальное количество файлов — 10".
  2. Возврат к шагу 4.


## UC-02. Отправка заявки на согласование

**Область действия:** Система управления закупочными заявками

**Уровень:** Цели пользователя

**Основное действующее лицо:** Сотрудник

**Участники:** Отсутствуют

**Предусловие:**
- Заявка существует в системе.
- Заявка находится в статусе "Черновик" или "На доработке".
- Пользователь является автором заявки.

**Гарантии успеха:**
- Заявка отправлена на согласование.
- Заявке присвоен статус "На проверке".
- Первый согласующий по маршруту получил уведомление.

**Триггер:** Сотрудник завершил заполнение заявки и готов отправить её на согласование.

**Описание:**
1. Сотрудник открывает заявку на редактирование.
2. Сотрудник проверяет заполнение всех полей.
3. Сотрудник нажимает кнопку "Отправить на согласование".
4. Система проверяет заполнение всех обязательных полей.
5. Система определяет маршрут согласования на основе выбранного типа закупки.
6. Система создаёт первый этап согласования (назначение руководителю).
7. Система изменяет статус заявки на "На проверке".
8. Система отправляет уведомление руководителю о новой заявке.
9. Система отображает сообщение: "Заявка отправлена на согласование".

**Расширения:**
- *4a. Система обнаруживает незаполненные обязательные поля:*
  1. Система подсвечивает незаполненные поля.
  2. Система отображает сообщение: "Заполните все обязательные поля перед отправкой".
  3. Возврат к шагу 1.
- *5a. Для выбранного типа закупки не настроен маршрут согласования:*
  1. Система изменяет статус заявки на "Ожидание настройки маршрута".
  2. Система отправляет уведомление администратору с текстом: "Для типа закупки '[тип]' не настроен маршрут. Требуется настройка".
  3. Система отображает сообщение: "Для данного типа закупки маршрут не настроен. Обратитесь к администратору".
  4. Use Case завершается.

**Уровень:** Цели пользователя

**Основное действующее лицо:** Сотрудник

**Участники:** Отсутствуют

**Предусловие:**
- Заявка существует в системе.
- Заявка находится в статусе "Черновик" или "На доработке".
- Пользователь является автором заявки.

**Гарантии успеха:**
- Заявка обновлена в системе.
- Изменения сохранены.
- Статус заявки не изменился (остался "Черновик" или "На доработке").

**Триггер:** Сотрудник хочет внести изменения в заявку.

**Описание:**
1. Сотрудник открывает заявку на редактирование.
2. Система отображает форму заявки с текущими данными.
3. Сотрудник изменяет необходимые поля.
4. Сотрудник может заменить или добавить документы.
5. Сотрудник нажимает кнопку "Сохранить".
6. Система проверяет заполнение обязательных полей.
7. Система сохраняет изменения.
8. Система отображает сообщение: "Заявка обновлена".

**Расширения:**
- *3a. Сотрудник пытается редактировать заявку в статусе, отличном от "Черновик" или "На доработке":*
  1. Система отображает сообщение: "Редактирование недоступно для заявок в статусе '[статус]'".
  2. Use Case завершается.


## UC-04. Принятие решения по заявке

**Область действия:** Система управления закупочными заявками

**Уровень:** Цели пользователя

**Основное действующее лицо:** Руководитель

**Участники:** Сотрудник (автор заявки), Система

**Предусловие:**
- Заявка существует в системе.
- Заявка находится в статусе "На проверке" или "На согласовании".
- Пользователь является ответственным согласующим на текущем этапе.

**Гарантии успеха:**
- Заявка переведена на следующий этап маршрута или завершена.
- Автор заявки получил уведомление о решении.
- История заявки пополнена записью о решении (или комментарии).

**Триггер:** Руководитель получает уведомление о необходимости принять решение по заявке.

**Описание:**
1. Руководитель открывает раздел "Заявки на согласование".
2. Система отображает список заявок, ожидающих решения руководителя.
3. Руководитель выбирает заявку для просмотра.
4. Система отображает полную информацию о заявке и прикреплённые документы.
5. Руководитель изучает информацию.
6. (Опционально) Руководитель может оставить комментарий к заявке в текстовом поле, не меняя её статуса.
7. Система сохраняет комментарий (если был оставлен) и отображает его в истории.
8. Руководитель выбирает одно из решений:
   - Согласовать
   - Вернуть на доработку
   - Отклонить
9. Если выбрано "Вернуть на доработку" или "Отклонить", руководитель заполняет поле "Причина" (обязательно).
10. Руководитель нажимает кнопку "Подтвердить решение".
11. Система проверяет заполнение причины (если требуется).
12. Система изменяет статус заявки в соответствии с решением:
    - "Согласована" (если это последний этап) или переход на следующий этап
    - "На доработке" (при возврате)
    - "Отклонена" (при отклонении)
13. Система сохраняет запись в истории заявки (включая решение, причину и комментарий, если они были).
14. Система фиксирует время выхода из текущего статуса (согласно UC-12).
15. Система отправляет уведомление автору заявки о принятом решении.
16. Система отображает сообщение: "Решение принято".

**Расширения:**
- *8a. Руководитель выбрал "Согласовать", но это не последний этап маршрута:*
  1. Система переводит заявку на следующий этап согласования.
  2. Система изменяет статус на "На согласовании".
  3. Система отправляет уведомление следующему согласующему.
  4. Возврат к шагу 16.
- *9a. Руководитель не заполнил причину при возврате или отклонении:*
  1. Система подсвечивает поле "Причина".
  2. Система отображает сообщение: "Укажите причину возврата/отклонения".
  3. Возврат к шагу 9.
- *11a. Руководитель передумал и закрыл форму:*
  1. Изменения не сохраняются.
  2. Use Case завершается.


## UC-05. Настройка маршрута согласования

**Область действия:** Система управления закупочными заявками

**Уровень:** Цели пользователя

**Основное действующее лицо:** Администратор

**Участники:** Отсутствуют

**Предусловие:**
- Пользователь авторизован в системе.
- Пользователь имеет роль "Администратор".

**Гарантии успеха:**
- Маршрут для типа закупки создан или изменён.
- Изменения сохранены в системе.

**Триггер:** Администратору необходимо настроить или изменить маршрут для типа закупки.

**Описание:**
1. Администратор открывает раздел "Настройка маршрутов".
2. Система отображает список существующих типов закупок и их маршрутов.
3. Администратор выбирает тип закупки для настройки.
4. Администратор добавляет или удаляет этапы согласования.
5. Для каждого этапа администратор указывает: роль согласующего, срок согласования.
6. Администратор нажимает кнопку "Сохранить".
7. Система проверяет корректность маршрута (наличие хотя бы одного этапа).
8. Система сохраняет маршрут.
9. Система отображает сообщение: "Маршрут сохранён".

**Расширения:**
- *4a. Администратор создаёт маршрут для нового типа закупки:*
  1. Администратор нажимает кнопку "Создать тип закупки".
  2. Вводит название нового типа.
  3. Добавляет этапы по шагам 4-5.
  4. Возврат к шагу 6.
- *7a. Администратор пытается сохранить маршрут без этапов:*
  1. Система отображает сообщение: "Маршрут должен содержать хотя бы один этап согласования".
  2. Возврат к шагу 4.


## UC-06. Добавление нестандартного этапа согласования

**Область действия:** Система управления закупочными заявками

**Уровень:** Цели пользователя

**Основное действующее лицо:** Администратор

**Участники:** Отсутствуют

**Предусловие:**
- Заявка существует в системе.
- Заявка находится в процессе согласования.
- Пользователь имеет роль "Администратор".

**Гарантии успеха:**
- Нестандартный этап добавлен в маршрут заявки.
- Заявка направлена на дополнительное согласование.
- Участники этапа получили уведомления.

**Триггер:** Администратор выявил необходимость дополнительного согласования для конкретной заявки.

**Описание:**
1. Администратор открывает заявку.
2. Администратор выбирает действие "Добавить этап согласования".
3. Система отображает форму для добавления этапа.
4. Администратор указывает: роль согласующего, срок согласования, комментарий.
5. Администратор нажимает кнопку "Добавить этап".
6. Система проверяет корректность введённых данных.
7. Система встраивает новый этап в текущий маршрут заявки.
8. Система отправляет уведомление ответственному согласующему.
9. Система отображает сообщение: "Дополнительный этап добавлен".

**Расширения:**
- *7a. Заявка уже находится на этапе, который должен быть завершён до добавленного:*
  1. Система изменяет статус заявки на соответствующий этап.
  2. Продолжение с шага 8.


## UC-07. Поиск и просмотр заявок

**Область действия:** Система управления закупочными заявками

**Уровень:** Цели пользователя

**Основное действующее лицо:** Сотрудник, Руководитель, Отдел закупок (любой авторизованный пользователь)

**Участники:** Отсутствуют

**Предусловие:**
- Пользователь авторизован в системе.
- В системе существуют заявки.

**Гарантии успеха:**
- Пользователь получил список заявок, соответствующих критериям поиска.
- Пользователь может просмотреть детальную информацию по каждой заявке.

**Триггер:** Пользователь хочет найти конкретную заявку или просмотреть список доступных заявок.

**Описание:**
1. Пользователь открывает раздел "Заявки".
2. Система отображает список заявок, доступных пользователю (в соответствии с его ролью).
3. Пользователь может применить фильтры: ID заявки, тип закупки, подразделение, статус, дата создания (диапазон).
4. Пользователь может отсортировать список по: дате создания, статусу, типу закупки.
5. Система отображает отфильтрованный и отсортированный список заявок.
6. Пользователь выбирает заявку для просмотра.
7. Система отображает полную информацию о заявке: все поля, документы, историю, текущий статус.

**Расширения:**
- *5a. Заявок, соответствующих критериям поиска, не найдено:*
  1. Система отображает сообщение: "Заявки не найдены. Попробуйте изменить параметры поиска".
  2. Система предлагает сбросить фильтры.
  3. Возврат к шагу 2.


## UC-08. Завершение заявки отделом закупок

**Область действия:** Система управления закупочными заявками

**Уровень:** Цели пользователя

**Основное действующее лицо:** Сотрудник отдела закупок

**Участники:** Сотрудник (автор заявки), Руководитель

**Предусловие:**
- Заявка существует в системе.
- Заявка находится в статусе "Согласована".
- Пользователь имеет роль "Отдел закупок".

**Гарантии успеха:**
- Заявка переведена в статус "Передана в отдел закупок".
- Автор и руководитель получили уведомление о завершении согласования.
- Дата завершения обработки зафиксирована.

**Триггер:** Согласованная заявка поступила в отдел закупок для дальнейшей обработки.

**Описание:**
1. Сотрудник отдела закупок открывает раздел "Заявки на исполнение".
2. Система отображает список заявок со статусом "Согласована".
3. Сотрудник отдела закупок выбирает заявку.
4. Система отображает полную информацию о заявке и прикреплённые документы.
5. Сотрудник отдела закупок проверяет корректность данных.
6. Сотрудник отдела закупок нажимает кнопку "Принять заявку".
7. Система изменяет статус заявки на "Передана в отдел закупок".
8. Система фиксирует дату и время завершения обработки заявки.
9. Система отправляет уведомления автору заявки и руководителю: "Заявка передана в отдел закупок".
10. Система отображает сообщение: "Заявка принята отделом закупок".

**Расширения:**
- *5a. Сотрудник отдела закупок обнаружил некорректные данные:*
  1. Сотрудник отдела закупок может добавить комментарий к заявке.
  2. Сотрудник отдела закупок связывается с автором для уточнения.
  3. Автор может создать новую заявку или отредактировать существующую (если статус позволяет).
  4. Use Case завершается.
- *6a. Сотрудник отдела закупок не готов принять заявку и откладывает её:*
  1. Статус заявки остаётся "Согласована".
  2. Use Case завершается.


## UC-09. Просмотр истории заявки

**Область действия:** Система управления закупочными заявками

**Уровень:** Цели пользователя

**Основное действующее лицо:** Сотрудник, Руководитель, Отдел закупок (любой пользователь с доступом к заявке)

**Участники:** Отсутствуют

**Предусловие:**
- Заявка существует в системе.
- Пользователь имеет доступ к заявке (является автором, согласующим или имеет соответствующую роль).

**Гарантии успеха:**
- Пользователь видит полную историю изменений заявки в хронологическом порядке.

**Триггер:** Пользователь хочет узнать, кто и когда изменял статус заявки.

**Описание:**
1. Пользователь открывает заявку для просмотра.
2. Пользователь переходит на вкладку "История".
3. Система отображает список событий в хронологическом порядке (от старых к новым).
4. Для каждого события отображается:
   - дата и время действия;
   - имя пользователя;
   - действие (создание, изменение, отправка, согласование, отклонение, возврат);
   - предыдущий статус;
   - новый статус;
   - комментарий (если был оставлен).
5. Пользователь может просмотреть всю историю.

**Альтернативные потоки:**
- *3a. У заявки нет истории:* Система отображает сообщение: "История отсутствует".


## UC-10. Управление уведомлениями

**Область действия:** Система управления закупочными заявками

**Уровень:** Цели пользователя

**Основное действующее лицо:** Система (автоматически)

**Участники:** Сотрудник, Руководитель, Отдел закупок

**Предусловие:**
- Произошло событие, требующее уведомления.
- У пользователя есть активный email и доступ к системе.

**Гарантии успеха:**
- Уведомление доставлено пользователю (внутри системы и по email).
- Пользователь может перейти к заявке по ссылке из уведомления.

**Триггер:** Изменение статуса заявки или приближение срока.

**Описание:**
1. Происходит событие, инициирующее уведомление (создание заявки, изменение статуса, возврат, отклонение, согласование, приближение срока).
2. Система определяет получателей уведомления (автор, руководитель, ответственный согласующий).
3. Система формирует уведомление со следующими данными:
   - номер заявки;
   - тип действия;
   - описание действия;
   - ссылка на заявку.
4. Система отправляет уведомление:
   - внутри системы (в раздел "Уведомления" пользователя);
   - по электронной почте.
5. Система сохраняет факт отправки в логах.

**Альтернативные потоки:**
- *4a. Уведомление по email не доставлено:* Система повторяет попытку отправки через 5 минут. После 3 неудачных попыток фиксирует ошибку в логах.


## UC-11. Просмотр и скачивание документов

**Область действия:** Система управления закупочными заявками

**Уровень:** Цели пользователя

**Основное действующее лицо:** Сотрудник, Руководитель, Отдел закупок (любой пользователь с доступом к заявке)

**Участники:** Отсутствуют

**Предусловие:**
- Заявка существует в системе.
- К заявке прикреплены документы.
- Пользователь имеет доступ к заявке (является автором, согласующим или имеет соответствующую роль).

**Гарантии успеха:**
- Пользователь просмотрел документ (в браузере) или скачал его на локальное устройство.

**Триггер:** Пользователь хочет ознакомиться с содержимым прикреплённого документа.

**Описание:**
1. Пользователь открывает заявку для просмотра.
2. Система отображает раздел "Прикреплённые документы" со списком всех файлов.
3. Для каждого файла отображается:
   - название файла;
   - размер;
   - дата загрузки;
   - иконка формата (PDF, DOC, XLS и т.д.).
4. Пользователь может выполнить одно из действий:
   - нажать на название файла для **скачивания**;
   - нажать на иконку "Просмотр" (глаз) для **предварительного просмотра** (доступно для PDF, JPG, PNG).
5. При скачивании система загружает файл на устройство пользователя.
6. При просмотре система открывает документ в новом окне или встроенном просмотрщике.

**Расширения:**
- *4a. Пользователь пытается скачать документ, но файл отсутствует на сервере:*
  1. Система отображает сообщение: "Файл не найден. Обратитесь к администратору".
  2. Use Case завершается.
- *4b. Пользователь выбрал просмотр для формата, не поддерживающего предпросмотр (DOC, XLS):*
  1. Система отображает сообщение: "Для данного формата доступно только скачивание".
  2. Возврат к шагу 4.


## UC-12. Автоматическая фиксация времени обработки

**Область действия:** Система управления закупочными заявками

**Уровень:** Системный (фоновый процесс)

**Основное действующее лицо:** Система (автоматически)

**Участники:** Отсутствуют

**Предусловие:**
- Заявка существует в системе.
- Произошло событие, изменяющее статус заявки.

**Гарантии успеха:**
- Время входа в новый статус зафиксировано в истории.
- Время выхода из предыдущего статуса зафиксировано в истории.
- Для заявки доступна информация о длительности нахождения в каждом статусе.

**Триггер:** Изменение статуса заявки (в результате выполнения UC-02, UC-04, UC-05, UC-06, UC-08).

**Описание:**
1. Происходит изменение статуса заявки (например, с "Черновик" на "На проверке").
2. Система фиксирует в истории заявки запись о времени **выхода** из предыдущего статуса:
   - `дата_выхода_из_[старый_статус]` = текущая дата и время.
3. Система фиксирует в истории заявки запись о времени **входа** в новый статус:
   - `дата_входа_в_[новый_статус]` = текущая дата и время.
4. Система сохраняет эти записи в разделе "Временные метки" или в общей истории заявки.

**Расширения:**
- *1a. Заявка создаётся впервые (статус "Черновик"):*
  1. Система фиксирует только время входа в статус "Черновик".
  2. Время выхода отсутствует (заявка только создана).
  3. Use Case завершается.
- *1b. Заявка завершена (статус "Отклонена" или "Передана в отдел закупок"):*
  1. Система фиксирует время входа в конечный статус.
  2. Система фиксирует время выхода из последнего активного статуса.
  3. Система дополнительно фиксирует общее время обработки заявки (разница между созданием и завершением).
  4. Use Case завершается.
